# 审查报告模板与分级标准

审查的产出是一份可执行的清单，不是散文。每条都要能回答四个问题：**在哪、为什么是问题、怎么改、改了有什么代价**。

## 一、报告骨架

```
# <工程/模块> C++ 优化与安全审查报告

目标标准：C++17（证据：CMakeLists.txt:12、compile_commands.json:3 -std=gnu++17；GCC 9.3.1 / CentOS 7.9）
审查范围：<目录或文件清单>（共 N 个文件、M 行）
审查方式：只读静态审查，未修改任何文件，未编译验证

## 结论摘要

- P0（必须修）：X 条 —— 泄漏 / 未定义行为 / 数据竞争 / 编译不过
- P1（建议修）：Y 条 —— 异常安全等级不足、明显性能损失、标准越界
- P2（可选）：Z 条 —— 风格、可读性、可维护性、后续演进
- 一句话判断：<这个模块当前是否满足「快且安全」，短板在哪>

## P0 问题

### P0-1 <标题>
- 位置：`src/foo.cpp:120-134`
- 维度：RAII 与所有权（见 references/raii-ownership.md）
- 现状：<贴出关键几行代码>
- 为什么是问题：<机制说明，引用标准或文档结论；说明触发条件>
- 影响：<泄漏 / UB / 崩溃 / 数据竞争 / 编译错误，能举例就举例>
- 修法：<给出改后代码>
- 代价与风险：<行为变化？性能影响？ABI？需要同步改的调用方>
- 验证方式：<用什么输入/测试/工具确认修好了>

## P1 问题

（结构同上）

## P2 问题

（结构同上，可简化为一行一条）

## 需要你决策的分歧

1. <问题>：选项 A（代价…）/ 选项 B（代价…）
2. ...

## 未验证项

- 未编译（本机无该工程工具链），未运行基准测试。
- 未确认 X 的行为契约，按现有代码推断。
```

## 二、分级标准

| 级别 | 判定依据 | 典型例子 |
|---|---|---|
| **P0** | 会导致未定义行为、资源泄漏、崩溃、数据竞争，或在目标标准下根本编译不过 | 裸指针 + 可抛异常；容器失效后继续用迭代器；多线程裸读改写；对 `nullptr` 解引用；越界下标；返回局部变量引用；在 C++17 工程写 `std::span` |
| **P1** | 不立即出错，但在异常路径、边界输入、规模增长后出问题；或已有明确性能损失且有数据支撑 | 移动构造未标 `noexcept` 导致 `vector` 退化拷贝；热点循环逐次分配；`O(n²)` 字符串拼接；缺 `reserve`；异常安全等级不足；锁粒度过大 |
| **P2** | 可读性、可维护性、一致性、后续演进成本，不直接影响当前正确性与性能 | 命名与项目约定不一致；接口参数过多；`const` 遗漏但无行为影响；可以编译期算的量留到运行期 |

判定原则：**先问「会不会错」，再问「快不快」，最后才问「好不好看」**。只有 P0/P1 需要给完整论证，P2 允许一行一条。

## 三、单条问题的写法要求

1. **位置**必填：`文件:行号` 或 `文件:起止行`；跨文件时全部列出。
2. **为什么**必须写机制，不写「不规范」「不推荐」这类空话。例如写「`shared_ptr` 的两处独立构造会生成两个控制块，两个计数各自归零后对同一对象 `delete` 两次」，而不是写「`shared_ptr` 用法错误」。
3. **反例→正例**：给出可粘贴的最小代码对比，不贴整段文件。
4. **标准标注**：写清该修法要求的最低标准；工程标准不足时给降级写法。
5. **代价**：性能建议必须说明收益的前提（数据规模、访问模式、硬件）。没有测量的写「预估」，不写「提升明显」。
6. **不确定就标注**：无法确认的调用契约、外部输入范围、线程模型，写成「待确认：……」，并在「需要你决策的分歧」里提出。

## 四、常见表述禁区

| 不要写 | 改成 |
|---|---|
| 「性能提升明显」 | 「在 N=1e6 时省去约 N 次堆分配；未实测」 |
| 「最佳实践要求……」 | 「原因是……（引用具体机制或标准条款）」 |
| 「这里有内存泄漏」 | 「`p` 在 120 行 `new`，135 行的 `risky()` 抛出时跳过 `delete`，此路径泄漏 `sizeof(T)` 字节」 |
| 「建议全部改用智能指针」 | 逐条列出哪些 `new`/`delete` 对需要改造，哪些栈对象更合适 |
| 「这里线程不安全」 | 「`counter` 被 `workerA`、`workerB` 同时执行 `++`，非原子读-改-写会丢更新」 |
| 「用 C++20 的 concepts 更清晰」 | 「工程是 C++17，保持 `enable_if`；升级到 C++20 后可简化为 concepts（需评估工具链）」 |

## 五、报告之外的交付要求

- 报告本身不改代码；用户选定条目后，按条目逐个改造，每改一条同步更新对应说明。
- 改动涉及行为语义（口径、精度、顺序、所有权）时，先在「需要你决策的分歧」中提出，得到确认再动。
- 交付时列出：已改条目、未改条目及原因、验证方式与结果、仍需用户确认的事项。
